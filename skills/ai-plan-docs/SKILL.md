# /ai-plan-docs — 작업 계획을 docs/plans/ 에 남겨두기

## 언제 돌리나

`/ai-plan-docs` 나 `$ai-plan-docs` 로 불렀을 때만 돌려. 대화에서 이름만 나온 건 호출이 아니야.
`disable-model-invocation` 이 그 경로를 막아두니까, 그럴 땐 실행하지 말고 슬래시로 불러달라고만 말해.
계획 짜기·문서화 얘기가 나왔다고 알아서 집어 들면 안 돼.

## 뭐 하는 스킬이냐면

쉽게 말하면 **"다음에 할 일"을 세션 밖으로 빼두는 스킬**이야.

대화에서 정한 계획은 세션이 끝나면 같이 날아가. 그래서 그걸 프로젝트 루트의
`docs/plans/<slug>/` 에 파일로 박아둬. 다음 세션은 이 폴더만 읽으면 뭘, 왜, 어디까지
했는지 바로 복원할 수 있어.

파일은 세 개고, 각자 맡은 게 달라. 섞이면 안 돼.

| 파일 | 답하는 질문 | 언제 바뀌나 |
|---|---|---|
| **spec.md** | 뭘 만드나 — 스펙·범위·완료 조건 | 시작 전에 한 번 쓰고, 스펙이 바뀔 때만 |
| **context.md** | 왜 시작했나 — 원래 요청·결정 이유·버린 대안 | 처음 쓰고 거의 안 바뀜 |
| **checklist.md** | 어디까지 했나 — 단계별 체크박스 | 작업하면서 계속 |

이 스킬은 **기록까지만** 해. 실제 작업은 사용자가 따로 시킬 때 시작해.

## 실행 순서

### 1. 프로젝트 루트부터 잡아

```bash
ROOT=$(git rev-parse --show-toplevel 2>/dev/null || pwd)
```

`docs/plans/` 는 항상 이 루트 기준이야. 서브 디렉터리에서 불렸어도 루트로 맞춰.

**이후 단계는 전부 `$ROOT` 로 경로를 써.** 상대경로로 쓰면 서브 디렉터리에서 불렸을 때
기존 폴더를 못 보고 지나쳐서, 아래 "조용히 덮어쓰지 마" 규칙이 그냥 무력화돼.

### 2. slug 정하기

`<slug>` 는 영문 kebab-case 로 해 (예: `chat-panel-ai-bridge`, `weight-zero-rule`,
`auto-save-server-ssot`).

- 이번에 합의한 작업의 핵심 명사구를 뽑아.
- 한국어 주제는 영어로 의역해 ("발생 가중치 0 규칙" → `weight-zero-rule`).
- `refactor`, `fix` 처럼 너무 뭉뚱그린 이름 하나만 쓰진 마.

사용자가 slug 를 줬으면 그대로 써. 후보가 하나로 딱 떨어지면 바로 가고, 두 개 이상
떠오르면 `AskUserQuestion` 으로 골라달라고 해.

### 3. 이미 있는지 확인

```bash
ls "$ROOT/docs/plans/<slug>/" 2>/dev/null
```

- 없으면 → 폴더 만들고 세 파일 생성.
- 있으면 → 사용자한테 물어봐:
  - 이어서 갱신 (기존 파일 Edit)
  - 새 slug 로 생성 (`<slug>-v2` 같은 걸 제안)
  - 덮어쓰기 (위험하니까 사용자가 직접 골라야 함)

### 4. 세 파일 쓰기

아래 "파일 템플릿" 골격 그대로 써. 헤더만 덩그러니 박아두지 말고
**대화에서 이미 합의된 내용으로 채워.** 아직 안 정한 건 "TBD — 첫 작업 착수 시 확정"
처럼 비어 있다는 게 티 나게 남겨.

### 5. 짧게 보고

만든 폴더랑 세 파일 경로만 보여주고 끝내. 바로 작업에 들어가지 마.

## 파일 템플릿

헤더 제목은 그대로 두고, 본문은 대화 내용으로 채워.

### spec.md

```markdown
# spec — <slug>

## 목표
한 줄 정의. 이 작업이 끝나면 뭐가 가능해지나.

## 범위
- 포함:
  - …
- 제외:
  - …

## 완료 조건 (Definition of Done)
- [ ] …
- [ ] …

## 인터페이스 / 데이터 형식
필요하면 함수 시그니처, JSON 스키마, 엔드포인트, 파일 경로 등.

## 의존성
- 외부 라이브러리·서비스·CLI:
- 먼저 끝나 있어야 하는 작업:

## 비고
일부러 뺀 부분, 가정, 알려진 제약.
```

### context.md

```markdown
# context — <slug>

## 사용자의 원 요청
사용자가 처음 이 작업을 꺼낸 말 (요약 또는 인용).

## 왜 이걸 지금 하는가
배경·동기. 어떤 문제·증상·요구 때문에 시작했나.

## 결정된 방향
여러 대안 중 뭘 골랐나. 한 줄로.

## 기각된 대안
- 대안 A — 버린 이유
- 대안 B — 버린 이유

## 제약 / 합의 사항
- 기술적 제약:
- 시간·범위 제약:
- 사용자가 밝힌 선호:

## 관련 자료
이 작업을 이해하는 데 필요한 파일·커밋·외부 문서 경로.
```

### checklist.md

```markdown
# checklist — <slug>

> 작업하면서 AI 가 순서대로 체크한다. `[x]` 는 끝난 항목이다.
> 새 항목이 생기면 맞는 단계에 끼워 넣는다.

## 0. 준비
- [ ] spec.md / context.md 다시 읽고 어긋난 데 없는지 확인
- [ ] 작업 브랜치 확인 또는 생성 (필요하면)

## 1. 구현
- [ ] …
- [ ] …

## 2. 검증
- [ ] 단위 동작 확인
- [ ] 회귀 확인 (영향 받는 기존 기능)
- [ ] (UI 가 있으면) 브라우저에서 직접 확인

## 3. 마무리
- [ ] (사용자가 커밋을 지시한 경우에만) 커밋 — 저장소의 `.claude/commands/commit.md` 와
      `CLAUDE.md` 의 Git 절을 먼저 읽고 그 규약을 따름
- [ ] 체크 안 된 항목이 남았으면 이유 메모
- [ ] 다음 세션이 이어받을 수 있게 spec.md / context.md 에 바뀐 점 반영
```

## 다른 스킬이 이 템플릿에 기대고 있어

`ai-interview-tech` 가 인터뷰 결과를 이 세 파일에 넘겨 (그 스킬의 `결정 스펙을 영속화한다` 절).

| 인터뷰 산출물 | 들어가는 곳 |
|---|---|
| 확정된 결정 표 + 근거 | `spec.md` / `context.md` |
| 논의에서 생략한 축 | `context.md` |
| 리뷰 검증 체크리스트 | `checklist.md` |

**세 파일의 헤더 구조를 바꾸면 저쪽 매핑도 같이 고쳐.** 한쪽만 고치면 넘기는 게 조용히 어긋나.

## 지켜야 할 것

- **파일은 한국어로 써.** 헤더의 영어 키워드(`spec`, `Definition of Done` 등)만 그대로 두고
  본문은 전부 한국어. slug 만 영문 kebab-case.
- **체크리스트는 살아 있어야 해.** 작업이 시작되면 진행하면서 `checklist.md` 를 `Edit` 으로
  `[ ]` → `[x]` 바꿔. 만들어놓고 잊어버리면 의미가 없어.
- **한두 개씩 진행하고 매번 체크해.** 항목을 몰아서 처리하고 한참 뒤에 한꺼번에 체크하면,
  중간에 컨텍스트가 끊겼을 때 어디까지 했는지가 파일에 안 남아. 파일 10개를 동시에 고치고
  나중에 몰아서 보고하는 식은 하지 마.
- **파일만 읽어도 이해되게 써.** "위에서 말한 대로", "앞서 논의한 방식" 같은 표현은 쓰지 마.
  다음 세션은 이 대화를 몰라.
- **스펙이 바뀌면 spec.md 부터 고치고 움직여.** 코드랑 스펙이 어긋난 채로 가면 다음 세션이
  틀린 정보를 집어 들어.
- **context.md 는 거의 얼려둬.** "왜 시작했나"는 나중에 안 바뀌어. 새 결정이 생기면 끝에
  `## 변경 이력` 섹션을 붙여서 append 해.
- **기존 plan 폴더는 절대 조용히 덮어쓰지 마.** 반드시 사용자 확인 받아.

## 다음 세션에서 이어가기

이 스킬이 진짜 값어치를 하는 건 여기야. 사용자가 폴더를 짚으면서 이어가자고 하면
(예: "docs/plans/chat-panel-ai-bridge 이어서 해줘") 이 순서로 맥락을 복원해.

1. `checklist.md` → 어디까지 했고 다음 미체크 항목이 뭔지
2. `context.md` → 왜 하는지, 결정·제약·버린 대안
3. `spec.md` → 전체 목표랑 완료 조건
4. 사용자한테 **"N/Total 완료, 다음은 X"** 식으로 짧게 보고
5. 확인 받으면 남은 항목부터 이어서 진행

보고하기 전엔 코드를 건드리지 마. 파일이 코드랑 어긋나 있을 수 있으니까, 그럴 땐
"스펙이 바뀌면 spec.md 부터" 규칙을 먼저 적용해.

## 출력 예시

```
docs/plans/chat-panel-ai-bridge/
├── spec.md       (구현 스펙)
├── context.md    (시작 맥락)
└── checklist.md  (진행 체크리스트)

다음 세션에서 이 폴더만 읽으면 이어갈 수 있어.
```
