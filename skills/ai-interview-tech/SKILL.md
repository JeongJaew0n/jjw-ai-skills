# AI Interview Tech

## 활성화 조건

`/ai-interview-tech` 나 `$ai-interview-tech` 로 불렀을 때만 돌려. 이름만 나온 건 호출이 아니야 — `disable-model-invocation` 이 그 경로를 막으니까, 실행하지 말고 슬래시로 불러달라고 안내해. 평범한 구현·설계 요청이나 기술 결정이 필요해 보이는 상황이라고 알아서 집어 들지 마.

## 이 스킬이 푸는 문제

AI가 코드를 많이 쓰게 되면 사람이 통제하는 지점이 코드 작성에서 의도 전달과 검증으로 옮겨가. 그런데 직접 코드를 안 쓴 만큼, 결과물이 어떤 판단을 거쳐 나왔는지 다시 확인하는 인지 부하가 생겨.

문제의 뿌리는 리뷰가 아니라 그 앞에 있어. 비즈니스 요구사항은 자연어로는 자연스럽게 들리지만, 코드 수준에서 보면 그 안에 기술 결정이 여러 개 숨어 있어. 자연어 요구사항을 그대로 구현 프롬프트로 넘기면 그 결정이 전부 AI 해석에 맡겨지고, 사람이랑 같이 논의한 적 없는 결정이 구현 어딘가에 박혀.

이 스킬의 목적은 딱 하나야. **요구사항 뒤에 숨은 기술 결정을 구현 전에 드러내고, 사람 판단이 필요한 부분을 숨기지 않고 같이 확정하는 것.**

핵심은 요구사항을 길게 쓰는 게 아니야. 어떤 결정이 필요한지 드러나는 구조를 만드는 거야.

## 하지 말아야 할 것

- 요구사항을 받자마자 구현으로 직행하지 마. 구현은 이 인터뷰가 끝난 다음이야.
- 결정을 사용자한테 통째로 떠넘기지 마. "어떻게 할까요?" 하고 넓게 묻는 건 인지 부하를 사용자한테 떠넘기는 거야.
- 추상적인 질문을 던지지 마. "실패 시 어떻게 처리할까요" 같은 질문은 사용자가 코드베이스 구조를 머릿속에 다시 올려야 하게 만들어.
- 결정을 조용히 내려버리지 마. AI가 마음대로 정한 결정은 리뷰 때 역추적 비용이 돼.

## 워크플로우

### 1단계 — 코드베이스부터 읽어

질문하기 전에 지금 코드베이스를 읽어. 똑같이 "알림을 보낸다"는 요구사항이라도 프로젝트마다 맞는 구현이 달라. 어떤 코드베이스엔 이미 outbox 패턴이 있고, 어떤 코드베이스는 동기 외부 호출이 기존 컨벤션이야. 어떤 서비스는 이벤트 발행이 표준이고, 어떤 서비스는 작업 큐나 배치 재시도를 써.

읽으면서 확인할 것:
- 이번 작업이랑 맞닿는 기존 패턴과 컨벤션은 뭔가
- 트랜잭션 경계, 에러 처리, 재시도, 이벤트 발행이 지금 어떻게 돼 있나
- 비슷한 기능이 이미 있으면 그 구현은 어떤 결정을 따랐나

코드베이스를 안 읽고 던지는 질문은 추상적일 수밖에 없어. 결정이 갈리는 지점은 코드 안에 있거든.

### 2단계 — 이번 작업의 결정 축을 골라

요구사항과 코드베이스를 본 다음, 이번 작업에서 실제로 결정이 갈리는 축만 골라내. 모든 축을 매번 묻진 마. 어떤 변경에선 Atomicity랑 Failure-mode가 핵심이고, 어떤 변경에선 Compatibility랑 Security가 핵심이야.

결정 축 카탈로그는 `references/decision-axes.md`에 있어. 처음 보는 작업 유형이거나 어떤 축이 중요한지 감이 안 오면 그 파일을 읽어.

다 골랐으면 사용자한테 지도부터 보여줘. 뭘 논의하고, 뭘 왜 빼는지 한눈에 보이게. 예:

```
이번 작업은 알림 발송 기능 추가로 보입니다.
핵심 결정은 Atomicity / Idempotency / Failure-mode 입니다.
Observability 는 실패 추적을 위해 짧게 확인하고,
Compatibility 는 기존 API 계약 변경이 없으므로 생략하겠습니다.
```

빼는 축은 왜 빼는지 밝혀. 그래야 사용자가 빠진 결정이 의도된 건지 판단할 수 있어.

### 3단계 — grill-me 방식으로 한 축씩 인터뷰해

고른 축을 결정이 갈리는 순서대로 하나씩 진행해. 축마다 네 가지 규칙을 지켜.

1. **한 번에 질문 하나만.** 여러 결정을 한꺼번에 묻지 마.
2. **질문엔 추천 답을 같이 내.** AI가 코드베이스를 근거로 선택지를 좁히고 추천안을 내. 사용자는 추천을 보고 확정하거나 뒤집으면 돼.
3. **추상 원칙보다 관련 코드를 먼저 보여줘.** 선택지를 코드로 보여줘야 질문이 구체적이 돼.
4. **결정이 갈리는 순서대로 물어.** 앞 결정이 뒤 결정을 좌우하면 앞엣것부터 확정해.

추상적인 질문이랑 코드 기반 질문은 이렇게 달라.

**나쁜 질문:**
```
알림 실패 시 어떻게 처리할까요?
```
너무 넓어. 사용자가 맥락이랑 코드베이스 구조를 다시 떠올려야 해.

**좋은 질문:**
```kotlin
// option A — 트랜잭션 안에서 바로 알림 전송
@Transactional
fun completeOrder(orderId: OrderId) {
    val order = orderRepo.get(orderId)
    order.markCompleted()
    notificationClient.send(order)
}

// option B — commit 후 발행할 outbox만 저장
@Transactional
fun completeOrder(orderId: OrderId) {
    val order = orderRepo.get(orderId)
    order.markCompleted()
    outboxRepo.save(NotificationRequested(order.id))
}
```
```
이 코드베이스에는 이미 outbox 테이블과 발행 worker 가 있습니다.
알림 실패가 주문 완료를 rollback 시키면 안 된다면,
B 처럼 commit 이후 발행하는 방식이 더 적합합니다.
이 방향으로 확정할까요?
```

예시는 Kotlin/Spring 이지만 **형식만 빌리면 돼** — 핵심은 선택지를 그 코드베이스의 실제 코드로 보여주는 거야.

인터뷰의 목적은 판단을 떠넘기는 게 아니라 그 반대야. AI가 코드베이스를 먼저 읽고, 가능한 선택지를 좁히고, 추천안을 내. 사용자는 거기서 "이 방향이 맞다" 아니면 "아니다"만 정하면 돼. 그래서 인지 부하가 줄어.

### 4단계 — 확정된 결정만 스펙에 적어

축이 하나 확정될 때마다 스펙에 반영해. 아직 확정 안 된 것, 사용자가 보류한 것은 적지 마. 잡담으로 흐른 부분도 적지 마.

인터뷰가 끝나면 아래 형태로 결정 스펙을 정리해. 이 스펙이 있으면 나중에 리뷰가 "코드 전체를 다시 해석하는 일"에서 "합의한 결정이 코드에 반영됐는지 확인하는 일"로 바뀌어.

**기준 커밋과 작성일은 꼭 넣어.** 이 결정은 특정 시점의 코드베이스를 읽고 내린 거야. 기준이 없으면 나중에 "이 결정이 지금도 유효한가"를 판단할 수 없고, `review-code-intent` 가 이 스펙을 출처 등급 `명시` 로 채택할 때 옛 기준을 지금 코드에 그대로 채점하게 돼.

```markdown
# 결정 스펙: <기능 이름>

> 기준 커밋: `<SHA>` / 작성일: <YYYY-MM-DD>

## 요구사항
<사용자가 준 비즈니스 요구사항 한 줄>

## 확정된 결정
| 결정 축 | 확정 내용 | 근거 |
|---|---|---|
| Atomicity | 주문 완료 commit 이후 outbox 로 알림 분리 | 알림 실패가 주문 완료를 rollback 시키면 안 됨, 기존 outbox worker 존재 |
| Idempotency | 주문 ID 기준 중복 방지 키 사용 | 이벤트 재처리 시 알림 1회 보장 |
| Failure-mode | 알림 실패는 주문 완료에 영향 없음, worker 가 재시도 | ... |

## 논의에서 생략한 축
| 결정 축 | 생략 이유 |
|---|---|
| Compatibility | 기존 주문 완료 API 계약 변경 없음 |

## 리뷰 검증 체크리스트
- [ ] 스펙에서 확정한 트랜잭션 경계가 코드에 반영됐는가
- [ ] 중복 방지 키가 합의한 기준대로 사용됐는가
- [ ] 실패한 알림이 주문 완료 상태를 흔들지 않고 재시도 가능하게 남는가
- [ ] 로그와 이벤트가 합의한 관측 지점을 제공하는가
```

## 인터뷰가 끝난 뒤

스펙이 확정되면 그때 구현으로 넘어가. 구현 프롬프트엔 자연어 요구사항이 아니라 확정된 결정 스펙을 근거로 넘겨.

리뷰 단계에선 위 검증 체크리스트를 기준으로 봐. 코드가 길어도 모든 줄을 같은 밀도로 읽지 마. 스펙에서 합의한 결정이 실제 구현에 어떻게 반영됐는지부터 봐.

### 결정 스펙을 영속화한다

확정된 결정 스펙이랑 검증 체크리스트는 **리뷰할 때, 다음 세션에서, 다른 PC에서 또 필요해.** 세션 메모리에만 두면 정작 쓸 때 사라져. 그래서 이 기준으로 파일에 박제해.

- **결정 축이 2개 이상이고 구현이 여러 세션에 걸치는 작업** → 영속화해.
- **축 1개짜리 단발 변경** → 대화 메모리로 충분하니까 생략해. (잡동사니 폴더를 만들지 마.)

영속화 방법엔 우선순위가 있어.

1. **`ai-plan-docs` 스킬이 있으면 그쪽에 맡겨.** 저장 규약을 따로 새로 만들지 마. 인터뷰 산출물은 그 스킬의 세 파일에 자연스럽게 대응돼.
   - 확정된 결정 표 + 근거 → `spec.md` / `context.md`
   - 논의에서 생략한 축 → `context.md`
   - 리뷰 검증 체크리스트 → `checklist.md`
   - 호출할 때 위에서 정리한 결정 스펙을 그대로 넘겨서 채워지게 해.

2. **`ai-plan-docs` 스킬이 없으면 결정 스펙을 md 파일로 직접 저장해.** `docs/decisions/<slug>.md` 에 4단계에서 정리한 결정 스펙 블록(요구사항 / 확정된 결정 / 생략한 축 / 리뷰 검증 체크리스트)을 그대로 써. `<slug>` 는 기능 이름을 영문 kebab-case 로 정해.

   **`docs/plans/` 안에는 쓰지 마.** 그 폴더는 `ai-plan-docs` 가 `spec.md` / `context.md` / `checklist.md` 세 파일로 관리해. 같은 폴더에 `decision-spec.md` 를 놓으면 나중에 `ai-plan-docs` 를 돌렸을 때 `spec.md` 랑 내용이 겹쳐서, 다음 세션이 어느 쪽을 정본으로 읽어야 할지 알 수 없게 돼.

어느 쪽이든 저장한 파일 경로를 사용자한테 짧게 알려줘. 그래야 다음 세션이 이어받아.

### 리뷰로 넘길 때

영속화한 결정 스펙은 `review-code-intent` 의 **의도 항목 1차 출처**가 돼. 그 스킬은 의도 항목에 출처 등급(`명시` / `확인` / `추론`)을 요구하고, `추론`(코드에서 역산한 것) 항목으론 미충족을 단정하지 못하게 막아.

인터뷰로 사람과 확정한 결정은 출처 등급 `명시` 야. **리뷰할 때 저장한 파일 경로를 같이 알려주면 코드에서 역산할 필요가 없어져.**

## 끝내기 전 자체 점검

인터뷰는 "언제 끝난 건지" 가 애매한 작업이야. 끝내기 전에 확인해.

- [ ] 선별한 축마다 확정 또는 명시적 보류가 있는가
- [ ] 생략한 축에 생략 이유가 붙어 있는가
- [ ] 각 질문에 추천안을 함께 냈는가 (넓게 떠넘긴 질문이 없는가)
- [ ] 코드를 보여주지 않고 추상적으로만 물은 축이 없는가
- [ ] 확정되지 않은 것을 스펙에 적지 않았는가
- [ ] 영속화 기준(축 2개 이상 + 여러 세션)에 따라 저장 여부를 판단했는가
- [ ] 저장했다면 경로를 사용자에게 알렸는가

## 전략과 전술의 구분

- **전술**은 grill-me 의 인터뷰 규칙을 빌려. 한 번에 하나, 추천안 포함, 코드 먼저, 갈리는 순서대로.
- **전략**은 그 질문들을 기술 결정 축으로 제한해. 인터뷰가 잡담으로 흐르지 않게, 구현 전에 놓치기 쉬운 결정만 다뤄.

둘 다 지켜야 인터뷰가 효과가 있어. 규칙만 있고 결정 축이 없으면 잡담이 되고, 축만 있고 규칙이 없으면 사용자한테 결정을 떠넘기게 돼.
