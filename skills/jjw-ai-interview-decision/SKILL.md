# jjw-ai-interview-decision

## 활성화 조건

`/jjw-ai-interview-decision` 나 `$jjw-ai-interview-decision` 로 불렀을 때만 돌려. 이름만 나온 건 호출이 아니야 — `disable-model-invocation` 이 그 경로를 막으니까, 실행하지 말고 슬래시로 불러달라고 안내해. 평범한 구현·설계 요청이라고 알아서 집어 들지 마.

## 이 스킬이 푸는 문제

자연어 요구사항엔 기술 결정이 여러 개 숨어 있어. 그걸 그대로 구현으로 넘기면 결정이 전부 AI 해석에 맡겨지고, 사람이랑 논의한 적 없는 결정이 코드 어딘가에 박혀. 리뷰 때 그걸 역추적하는 게 비용이야.

그래서 이 스킬은 구현 전에 세 가지를 해.

1. 코드를 읽고 **맥락별로 설계**를 써. 설계의 추천안이 깔고 있는 가정을 드러내.
2. 그 가정을 **라벨 붙은 결정 질문**(`Q-C4`, `P1`)으로 뽑아. 대화에서 번호로 바로 짚을 수 있게.
3. 사람이랑 **P1 부터 하나씩** 정하고, 정한 건 바로 문서의 결정 칸에 박아. 그 칸이 정본이 돼.

핵심은 질문을 많이 하는 게 아니야. 결정이 필요한 지점을 **번호로 부를 수 있는 구조**로 만들고, 정해진 것과 안 정해진 것을 언제든 구분할 수 있게 하는 거야.

## 하지 말아야 할 것

- 요구사항을 받자마자 구현하지 마. 구현은 P1 이 다 정해진 다음이야.
- "어떻게 할까요?" 처럼 넓게 떠넘기지 마. 질문엔 선택지와 추천이 꼭 붙어.
- 코드를 안 읽고 추상적으로 묻지 마. 배경엔 근거 파일·커밋이 붙어야 해.
- 결정을 조용히 내려버리지 마. 추천을 따른 것도 사람이 확정해야 결정이야.
- 확인 안 한 걸 사실처럼 쓰지 마. `[확정: 근거]` · `[가정]` · `[미정]` 으로 나눠.

## 산출물 — 문서 네 개

`docs/plans/<slug>/` 에 둬. `<slug>` 는 작업을 나타내는 영문 kebab-case 야(티켓 번호를 넣어도 돼: `npt-1776-application-delete-worker`).

| 파일 | 답하는 질문 | 언제 바뀌나 |
|---|---|---|
| `계획서.md` | 무엇을 어떻게 만드나 — 맥락별 설계, 추천안, 위험 | 결정이 설계를 바꿀 때마다 |
| `결정-질문.md` | 무엇을 정해야 하나 — 질문 · 선택지 · 추천 · **결정 칸** | 결정할 때마다. 결정의 정본 |
| `맥락노트.md` | 왜 이렇게 됐나 — 핵심 파일, 제약, 결정 로그, 함정 | 결정 · 함정이 생길 때 |
| `체크리스트.md` | 어디까지 했나 — Phase 별 항목과 블로커 | 작업하면서 계속 |

**프로젝트에 계획 문서 규약이 이미 있으면 그걸 따라.** 예를 들어 `ai-plan-docs` 를 쓰는 프로젝트면 `spec.md` · `context.md` · `checklist.md` 가 위 세 파일 자리고, `결정-질문.md` 만 더해. 저장소 `CLAUDE.md` 나 프로젝트 스킬에 정해진 이름이 있으면 그 이름을 써. 같은 폴더에 같은 역할 파일을 두 벌 만들지 마 — 다음 세션이 어느 쪽이 정본인지 모르게 돼.

문서 골격은 `references/document-templates.md` 에 있어. 처음 쓸 때 열어.

### 근거 표기

모든 문서에서 같은 표기를 써.

- `[확정: <근거>]` — 코드 · 커밋 · 실행 결과로 봤다. 근거는 `ClassName.method`, `파일:줄`, 커밋 SHA 처럼 다시 찾을 수 있게
- `[가정: <무엇을 보면 확인되나>]` — 안 봤다. 확인할 방법을 같이 적어
- `[미정]` — 결정이 안 됐다. 어느 질문이 정하는지 `(→ Q-B2)` 로 이어

## 질문 라벨링

### 번호 — `Q-<영역 문자><번호>`

- **영역**은 결정의 성격으로 묶어. 예: `A. 흐름과 범위` · `B. 상태 모델과 DB` · `C. 실행 동작` · `D. 외부 연동` · `E. 화면 계약` · `F. 인프라와 배포` · `G. 구현 방식`. 작업마다 다시 정하되 5~8개 안으로.
- 영역이 계획서의 맥락과 꼭 1:1 일 필요는 없어. 계획서는 **만드는 순서**로, 질문은 **결정의 성격**으로 나뉘어.
- 번호는 한 번 붙이면 바꾸지 마. 대화 · 커밋 · 다른 문서가 그 번호로 가리켜. 질문이 필요 없어지면 지우지 말고 결정 칸에 「불필요해졌다(Q-A3 으로 해소)」 처럼 적어.
- 나중에 질문이 생기면 그 영역의 끝 번호 다음으로 붙여.

### 우선순위 — `P1` / `P2` / `P3`

| 등급 | 뜻 | 기준 |
|---|---|---|
| **P1** | 구현을 시작하기 전에 필요하다 | 답에 따라 외부 경로 수 · 표 모양 · API 모양 같은 **구조**가 달라진다 |
| **P2** | 그 부분을 구현하기 전에 정하면 된다 | 답이 한 구성요소 안에서 끝난다 |
| **P3** | 나중에 정해도 된다 | 정하지 않으면 추천안으로 간다 |

### 질문 하나의 모양

```markdown
### Q-C5. resourceVersion 이 바뀐 리소스 (P2)

**배경.** <사실 2~4줄, 근거 표기 포함. 왜 이게 결정이 필요한지>

**선택지**

- (가) <구체적 행동>. <결과·비용>
- (나) <구체적 행동>. <결과·비용>

**추천: (가).** <왜 — 한두 줄. 측정이 필요하면 무엇을 재서 바꿀지>

**결정:**
```

- 선택지는 `(가)(나)(다)` 로 붙여. 대화에서 "다로 가자" 로 답할 수 있게.
- 선택지는 **코드에서 실제로 무엇이 달라지는지**로 써. 필요하면 짧은 코드 조각을 붙여.
- 조직 · 사람이 정할 문제(티켓 구성, 누가 할지)는 추천 대신 「정해 달라」 로 써도 돼. 기술 질문엔 꼭 추천을 내.

### 한눈에 보기 표

`결정-질문.md` 맨 위에 모든 질문을 한 줄씩 둬: `| 번호 | 질문 | 추천 | 우선 |`. 결정되면 추천 칸을 `✅ <결정 요약>(<날짜>)` 로 바꿔. 표만 봐도 남은 게 보이게.

## 워크플로우

### 1단계 — 큰 맥락 지도부터

요구사항을 받으면 바로 세부로 들어가지 말고, 작업이 어떤 **큰 맥락** 3~7개로 나뉘는지 먼저 보여줘. 맥락은 「따로 만들고 따로 배포할 수 있는 덩어리」야. 예: 외부 연동 경로 / 비밀 · 배포 설정 / DB / 애플리케이션 / 배포 · 검증.

```
이번 작업은 다섯 맥락으로 나뉘어.
1. SECloudit 위임 경로 — worker 가 사용자 토큰 없이 부를 길
2. OpenBao · helm — 그 토큰을 파드에 넣는 길
...
```

사용자가 맥락을 고치면 그걸 따라. 이 지도가 계획서의 목차가 돼.

### 2단계 — 맥락별 설계를 계획서에

맥락마다 코드를 읽고 「지금 [확정]」 → 「추가 · 변경할 것」 → 「주의할 점」 순으로 써.

읽으면서 볼 것:
- 이번 작업이랑 맞닿는 기존 패턴 · 선례(비슷한 기능이 이미 어떤 결정을 따랐나)
- 트랜잭션 경계, 실패 처리, 재시도, 권한 판정이 지금 어디서 일어나나
- 바꾸면 안 되는 기존 동작과 그걸 쓰는 곳

계획서 끝엔 **위험 표**(`위험 | 근거 | 대응`)를 둬. 대응이 질문이면 `→ Q-A2` 로 이어.

### 3단계 — 추천안의 가정을 질문으로 뽑아

계획서의 추천안이 깔고 있는 가정마다 「이게 틀리면 설계가 바뀌나?」 를 물어. 바뀌면 질문이야. 빠뜨린 게 없는지 `references/decision-axes.md` 의 축(Atomicity · Idempotency · Failure-mode · Compatibility · Security …)으로 한 번 훑어.

질문을 다 뽑으면 영역 · 번호 · 우선순위를 붙이고 `결정-질문.md` 를 써. 계획서 본문에서 그 결정에 기대는 자리엔 `(→ Q-xx)` 를 달아.

### 4단계 — 문서 검토를 받고 P1 부터 결정해

문서 경로를 알려주고 검토를 부탁해. 그다음 P1 부터 **하나씩** 진행해.

- **한 번에 질문 하나.** 사용자가 "하나씩 보자" 고 하면 더더욱.
- 대화에선 문서를 복붙하지 말고 **짧게 다시 설명해.** 공식 용어 먼저, 실제 런타임 흐름(A → B → C), 선택지별로 코드에서 뭐가 달라지는지, 추천과 이유 한 줄.
- 사용자가 되물으면(「이건 뭐야?」 「Argo 는 어떻게 해?」) 그 질문에 먼저 답해. 모르는 건 코드나 문서를 확인하고 답해. 추측으로 메우지 마.
- 사용자가 새 선택지를 내면 `(라)` 로 더하고 그걸 평가해. 사용자가 이미 정한 걸 다시 꺼내지 마.
- 결정 과정에서 배경 사실이 틀렸다고 드러나면 배경을 고치고 그 사실을 밝혀.
- **P3 와 뻔한 P2 는 묶어서 제안해**: 「Q-A4, A5, B3 … 는 추천안대로 일괄 확정할까?」 승인되면 각 결정 칸에 「추천안 일괄 확정(<날짜>)」 이라고 적어.

### 5단계 — 정할 때마다 바로 기록해

결정 하나가 나오면 그 자리에서 이걸 다 해. 몰아서 하면 빠뜨려.

1. `결정-질문.md` 결정 칸: `**결정:** <무엇을 · 범위 · 예외>. <근거 한 줄>. <날짜> 사용자 확정.`
2. 한눈에 보기 표의 추천 칸을 `✅ …(<날짜>)` 로
3. `맥락노트.md` 결정 로그에 한 줄(`| 시점 | 결정 | 이유 | 대안 |`)
4. 결정이 설계를 바꾸면 `계획서.md` 해당 절을 고쳐(위험 표의 대응 포함)
5. 새 작업이 생기거나 사라지면 `체크리스트.md` 를 고쳐
6. 결정이 다른 질문을 풀어 버리면 그 질문 결정 칸에 「불필요해졌다(<번호>)」

범위 밖 문제가 결정 중에 드러나면 결정 칸에 「범위 밖: …」 으로만 적고 손대지 마. 밖으로 나가는 일(티켓 · 문서 공유 · 푸시)은 따로 승인받아.

### 6단계 — 구현으로 넘어갈 때

- P1 이 다 정해지면 구현해. 남은 P1 이 실측 · 다른 사람 답을 기다리면, 그 답과 무관한 Phase 부터 해도 되는지 물어.
- 구현 중엔 **라벨을 인용해.** 코드 주석 · 커밋 본문 · 티켓 댓글에 `(NPT-1917 Q-C5)` 처럼. 리뷰가 코드에서 결정으로 바로 거슬러 올라가게.
- 구현하다 결정과 다르게 가야 하면 코드부터 고치지 말고, 그 질문을 다시 열어 사용자한테 말해.

## 단계 나누기 — 체크리스트의 Phase

- **Phase 0 · 결정과 실측** — P1 결정, 측정이 필요한 질문의 실측, 결정을 문서에 반영, 티켓 · 브랜치 준비.
- **Phase 1~N** — 의존 순서로. 다른 저장소 · 다른 팀 선행 → 비밀 · 인프라 → DB → 애플리케이션 → 검증 · 배포 → 화면 계약 전달 · 정리.
- 항목 하나는 커밋 1~2개 크기로. 상태는 `[대기]` · `[진행중]` · `[완료]`, 맨 위에 `진행 상태: N/Total`.
- 커밋 · push 상태는 항목에 같이 적어(`커밋 b9f46020, 로컬, push 는 승인 뒤`). 다음 세션이 원격 상태를 착각하지 않게.
- 맨 아래 `이슈 & 블로커` 표(`# | 이슈 | 상태 | 해결 방법`). 블로커가 질문이면 번호로 이어.

## 영속화와 리뷰 연결

- **질문이 3개 이하이고 한 세션에 끝나는 작업**이면 문서 네 개를 만들지 마. 대화에서 같은 라벨 방식으로 묻고, 끝에 결정만 요약해.
- 그 밖엔 문서로 남겨. `docs/plans/` 를 git 이 추적하지 않는 저장소도 있어. 그럼 끝났을 때 확정 설계를 어디로 옮길지(예: `docs/architecture/`)를 P3 질문으로 하나 넣어.
- `review-code-intent` 는 `결정-질문.md` 의 결정 칸을 의도 항목의 1차 출처(`명시`)로 써. 리뷰를 부탁할 땐 그 경로를 같이 넘겨.

## 끝내기 전 자체 점검

- [ ] 맥락 지도를 먼저 보여주고 사용자 확인을 받았는가
- [ ] 모든 질문에 번호 · 우선순위 · 배경 근거 · 선택지 · 추천(또는 「정해 달라」)이 있는가
- [ ] 결정된 질문마다 결정 칸 · 표 · 결정 로그가 같이 고쳐졌는가
- [ ] 결정 때문에 바뀐 사실이 계획서 · 체크리스트에 반영됐는가
- [ ] `[가정]` 으로 남은 것마다 확인 방법이 적혀 있는가
- [ ] 남은 P1 과 그 이유(실측 대기, 사람 대기)를 사용자에게 알렸는가
