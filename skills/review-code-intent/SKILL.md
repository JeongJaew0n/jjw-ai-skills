# review-code-intent

하나의 PR을 **성격이 다른 세 문서**로 나눠 리뷰한다.

| 문서 | 독자 | 답해야 할 질문 |
|---|---|---|
| `intent-review.md` | **사람** | 무엇이 왜 어떻게 달라졌는가 |
| `tech-review.md` | **AI / 후속 리뷰** | 이 구현이 실제로 안전하게 동작하는가 |
| `intent-implementation-review.md` | **AI / 후속 리뷰** | 이 구현이 의도를 달성했는가 |

**세 문서를 섞어 쓰지 않는다.** Intent에 클래스명·스택트레이스가 나오거나, Tech에 "이 기능은 백업을 편하게 해줍니다" 같은 설명이 들어가면 분리 실패다.

## Tech 와 Intent Implementation 의 경계

셋 중 가장 헷갈리는 지점이다. 기준은 하나다.

| 상황 | 문서 |
|---|---|
| 코드가 **의도한 대로** 동작하지 않는다 | `tech-review.md` |
| 코드는 정상 동작하는데 **의도한 것이 아니다** | `intent-implementation-review.md` |

Tech Review는 의도가 옳다고 **가정하고** 결함을 찾는다. Intent Implementation Review는 결함이 없다고 **가정하고** 의도 달성도를 측정한다.

의도가 `"재시도 3회 후 실패하면 담당자에게 알린다"` 일 때:

| 발견 | 문서 | 이유 |
|---|---|---|
| 재시도 카운터가 4회 돈다 | Tech | 구현 결함 |
| 알림 조건이 실패가 아니라 성공에 걸려 있다 | Tech | 잘못된 조건 판정 |
| 재시도는 되는데 알림이 아예 없다 | Intent Implementation | 의도 미충족 — 코드 자체는 정상 |
| 요구에 없던 강제 재시도 API가 추가됐다 | Intent Implementation | 과잉 |

같은 발견을 두 문서에 중복 기재하지 않는다.

## 대상 저장소 결정

**추측하지 않는다.** 현재 리포에서 실제 값을 확인한다.

```bash
git remote get-url origin
gh repo view --json owner,name,url 2>/dev/null
```

- 호스트가 `github.com` 이면 `--hostname` 없이 호출
- 그 외(GitHub Enterprise)면 **항상 `gh api --hostname {host} ...`** 로 호스트를 명시한다. `gh pr view` 가 된다고 `gh api` 가 같은 호스트로 붙지 않는다 (`404 Not Found`)

PR 번호가 인자로 없으면 현재 브랜치 기준으로 감지한다. 모호하면 묻는다.

base 브랜치는 **PR이 실제로 지정한 base** 를 쓴다. 레포 관례와 다르면 그 사실을 문서에 남긴다.

## 수행 순서

이 순서를 지킨다. 특히 **7번(의도 항목 동결)까지 끝나기 전에 Tech Review를 쓰기 시작하지 않는다.** 구현 결함을 먼저 보면 의도 파악이 그쪽으로 끌려가고, 요구사항 목록을 구현에 맞춰 역산하게 된다.

게이트를 6번이 아니라 7번에 거는 이유 — 6번만 끝내고 9번으로 건너뛰면 문구는 지켜지지만 **동결이 빠져 오염을 막지 못한다.**

1. PR 제목·본문·base/head·head SHA 확인
2. 변경 파일 목록 확인 (`status`: added/modified/removed 포함)
3. diff 확보. **diff만 보지 않는다** — 호출부, 호출 대상, 데이터 모델, 기존 테스트를 함께 읽는다
4. 변경 **전** 동작과 변경 **후** 동작을 각각 재구성한다
5. PR의 의도와 비즈니스 흐름을 파악한다
6. `intent-review.md` 작성
7. **의도 항목 목록을 확정한다** — 아래 `의도 항목 확정` 참조. 이 목록을 여기서 동결한다
8. 관점을 바꿔 구현을 다시 읽는다 (아래 Tech Review 검토 대상 기준)
9. `tech-review.md` 작성
10. 7번에서 동결한 목록으로 `intent-implementation-review.md` 작성
11. 세 문서가 같은 내용을 반복하지 않는지 확인

```bash
gh api [--hostname {host}] repos/{owner}/{repo}/pulls/{n} \
  --jq '{number,title,body,base:.base.ref,head:.head.ref,sha:.head.sha,url:.html_url,changed_files,additions,deletions}'

gh api [--hostname {host}] repos/{owner}/{repo}/pulls/{n}/files --paginate \
  --jq '.[] | {f:.filename, status:.status, add:.additions, del:.deletions}'

git diff origin/{base}...origin/{head} -- {path}     # gh pr diff 는 파일 경로 인자를 받지 않는다
```

리뷰 중 브랜치에 새 커밋이 쌓일 수 있다. **분석에 쓴 SHA를 문서에 기록**하고, 끝낼 때 head가 그대로인지 다시 확인한다.

## 산출물

리포지토리 루트 기준.

```
docs/reviews/
└── 381 Add backup retry policy/
    ├── intent-review.md
    ├── tech-review.md
    └── intent-implementation-review.md
```

### 폴더명 규칙

`[PR번호] [PR이름]` — 번호와 이름 사이 공백 하나.

PR 제목을 그대로 쓰되 파일시스템에서 못 쓰는 문자를 정리한다.

| 처리 | 대상 |
|---|---|
| `-` 로 치환 | `/ \ : * ? " < > \|` |
| 공백 하나로 축약 | 연속 공백·개행·탭 |
| 제거 | 앞뒤 공백, 끝의 `.` |
| 자름 | 폴더명 200자 초과 시 |

티켓 번호·프로젝트 태그가 접두로 붙은 제목(`#PROJ-123: [Area] 설명`)은 **접두를 제거하지 말고 치환만 한다** — 나중에 검색 키가 된다.

### 기존 폴더가 있으면

**덮어쓰지 않는다.** 먼저 읽고 최신 PR 상태 기준으로 **갱신**한다.

- 이미 해소된 Issue → 삭제하지 말고 해소됐음을 표시하고 근거(커밋 SHA 등)를 남긴다
- 판단이 뒤집힌 항목 → **정정 사실과 이유를 남긴다.** 조용히 고치면 다음 리뷰어가 같은 오판을 반복한다
- 어느 SHA 기준 리뷰인지 문서 상단에 기록한다

# 1. Intent Review

**목표는 구현 설명이 아니라 의도와 동작 변화의 이해다.**

리뷰어가 이 문서만 읽고 `"그래서 이 PR에서 뭐가 바뀌었어요?"` 에 답할 수 있어야 한다.

템플릿: `templates/intent-review.md`

## 답해야 할 질문

- 이 PR은 왜 필요한가
- 기존에는 어떻게 동작했는가
- 이번 PR로 무엇이 달라졌는가
- 사용자 요청 / 비즈니스 요구사항은 무엇인가
- 주요 비즈니스 로직은 어떤 흐름으로 동작하는가
- 정상 흐름은 어떻게 되는가
- 실패·예외 상황에서는 어떻게 동작하는가
- 기존 기능 중 영향받는 부분은 무엇인가
- 리뷰어가 반드시 기억해야 할 핵심은 무엇인가

## 작성 원칙

### 구현이 아니라 흐름을 쓴다

클래스명·메서드명·구현 세부사항은 **가능하면 숨긴다.**

```
[나쁨] FooService.process() 에서 validate() 호출 후 FooRepository.save() 를 수행한다.

[좋음] 요청을 받으면 먼저 처리 가능한 상태인지 검증한다.
       검증에 성공하면 상태를 변경하고 저장한다.
       처리할 수 없는 상태라면 기존 데이터를 변경하지 않고 요청을 거절한다.
```

코드 구조를 몰라도 기능 동작을 설명할 수 있는 문서여야 한다.

### 구현 세부사항은 예외적으로만 쓴다

기술적 선택이 **기능의 의미를 바꾸는 경우에만** 짧게 언급한다.

| 언급함 | 언급 안 함 |
|---|---|
| "관리자 화면과 사용자 화면이 서로 다른 저장소를 보기 때문에 배포를 각각 해야 한다" | "RestClient로 프록시 호출한다" |
| "동시에 실행하면 결과가 섞일 수 있어 한 번에 하나만 처리된다" | "분산락 어노테이션을 적용했다" |
| "잘못된 값을 보내면 저장하지 않고 거절한다" | "ValidationException을 던진다" |

### 분량

한 화면에 들어오는 길이를 목표로 한다. 길이가 아니라 **설명 가능성**이 품질 기준이다.

# 2. Tech Review

**목표는 잠재적 버그·장애 가능성·유지보수 위험을 찾는 것이다.** 구현 세부사항을 적극적으로 분석한다.

사람이 PR 전체를 학습하기 위한 문서가 아니다. AI가 후속 리뷰에서 다시 읽고 이어서 분석할 수 있을 만큼 **구체적으로** 남긴다.

템플릿: `templates/tech-review.md`

## 검토 대상

| 축 | 항목 |
|---|---|
| 정확성 | 논리 오류, 누락된 예외 처리, 잘못된 상태 전이 |
| 데이터 | 정합성, 트랜잭션 경계, 실패 시 rollback / partial update |
| 동시성 | race condition, 락 범위·수명, 중복 실행 |
| 경계 | null / empty / boundary case |
| 회귀 | 기존 기능 regression, API contract 변경, DB schema·query 영향 |
| 성능 | N+1, 루프 내 I/O, 불필요한 반복 조회 |
| 보안 | 권한 검증 누락, 잘못된 validation, 리소스 누수 |
| 테스트 | 테스트 누락, **테스트는 있으나 실제 위험을 검증하지 못하는 경우** |
| 유지보수 | 과도한 복잡도, 기존 프로젝트 패턴/아키텍처 이탈 |

리포에 코딩 규약 문서나 도메인 skill(`CLAUDE.md`, `AGENTS.md`, `.claude/skills/**`)이 있으면 **먼저 읽고 그 규칙을 함께 적용한다.** 프로젝트 고유 규약 위반은 일반론보다 우선한다.

## 지적하지 않는 것

실제 유지보수성이나 장애 가능성에 영향이 없다면 제외한다.

- 변수명 취향
- 개인적으로 선호하는 다른 패턴
- formatting

## Issue 형식

```markdown
### [Severity] 문제 제목

**위치** — 파일 / 클래스 / 메서드 (`path:line`)
**문제** — 무엇이 잘못될 수 있는지
**발생 조건** — 어떤 상황에서 발생하는지
**영향** — 서비스나 데이터에 어떤 영향을 주는지
**근거** — 왜 문제라고 판단했는지 (확인 방법 포함)
**제안** — 가능한 수정 방향
```

Severity는 `Critical` / `High` / `Medium` / `Low` 넷 중 하나.

| Severity | 기준 |
|---|---|
| Critical | 데이터 손실·유실, 보안 침해, 운영 중단 |
| High | 잘못된 비즈니스 동작, 회귀, 재현 가능한 결함 |
| Medium | 특정 조건에서만 드러나는 결함, 구조적 위험 |
| Low | 실질 위험은 낮으나 유지보수에 부담 |

### 확신도를 표시한다

확신이 낮은 내용을 확정 버그처럼 쓰지 않는다.

> **확인 필요** — 코드만으로 판단 불가. 무엇을 확인하면 결론이 나는지 함께 적는다.

> **잠재적 위험** — 메커니즘은 성립하나 실제 발생 조건이 미확인.

## 근거 등급을 반드시 구분한다

Tech Review에서 가장 흔한 실패는 **추론을 사실처럼 쓰는 것**이다. 각 Issue의 `근거`에 어느 등급인지 명시한다.

| 등급 | 의미 | 표기 |
|---|---|---|
| 실행 확인 | 테스트를 돌리거나 재현했다 | `실행 확인 — <명령/출력 요약>` |
| 코드 확정 | 코드 배선을 읽어 논리적으로 확정 | `코드 확정 — <파일:라인>` |
| 미측정 추정 | 메커니즘은 맞으나 실제 발생 여부 미확인 | `미측정 — <무엇을 재야 하는지>` |

**미측정 항목은 Severity를 올리지 않는다.** 재현되지 않은 위험은 재현된 결함과 같은 등급일 수 없다.

가능하면 추정에 머물지 말고 **실제로 돌려서 확인한다.** 단위 테스트 한 건, 로컬 재현 한 번이 추론 열 줄보다 낫다. 대조군(문제 원인이라 지목한 것만 제거한 버전)까지 확인하면 인과까지 확정된다.

재현 코드는 **커밋하지 않는다.** 임시 워크트리나 scratchpad에서 돌리고, 만든 임시 DB·브랜치·워크트리는 정리한다.

# 3. Intent Implementation Review

**목표는 결함 찾기가 아니라 의도 달성도의 측정이다.** "구현이 잘 됐다" 를 감상으로 쓰지 않고, 의도 항목마다 판정을 붙인다.

`intent-review.md` 가 **무엇을 하려 했는지**를 쓴 문서라면, 이 문서는 **그것이 실제로 됐는지**를 항목별로 채점한 문서다.

템플릿: `templates/intent-implementation-review.md`

## 의도 항목 확정

측정의 전제는 **측정 대상 목록**이다. 이 목록을 구현 결함을 읽기 전(수행 순서 7번)에 동결한다.

구현을 깊이 읽은 뒤에 목록을 만들면 **구현에 맞춰 요구사항을 역산**하게 된다. 그러면 무엇을 채점해도 충족으로 나온다.

### 인터뷰 산출물이 있으면 먼저 찾는다

```bash
ls docs/plans/*/spec.md docs/decisions/*.md 2>/dev/null
```

`ai-interview-tech` 가 구현 전에 사람과 확정한 결정 스펙이 있으면 **그것을 의도 항목의 1차 출처로 쓴다.** 출처 등급은 `명시` 다. 코드에서 역산하지 않는다.

각 항목에 **출처 등급**을 붙인다.

| 등급 | 의미 | 판정에 쓸 수 있는가 |
|---|---|---|
| 명시 | PR 본문·이슈·티켓에 문장으로 있다 | 그대로 쓴다 |
| 확인 | 사람에게 직접 확인받았다 | 그대로 쓴다 |
| 추론 | 코드·맥락에서 유추했다 | **미충족으로 단정하지 않는다** — `확인 필요` 로 남긴다 |

`추론` 항목으로 미충족을 매기는 것은 순환이다. 내가 코드에서 만들어낸 요구사항으로 그 코드를 채점하는 셈이다.

## 판정

| 판정 | 기준 |
|---|---|
| 충족 | 의도한 동작이 구현돼 있고 근거로 확인됐다 |
| 부분 충족 | 핵심 경로는 되지만 일부 조건·예외 경로가 빠졌다 |
| 미충족 | 구현되지 않았다 |
| 과잉 | 의도 근거가 없는 동작이 추가됐다 |
| 판정 불가 | 코드만으로 결론이 나지 않는다 |

근거는 Tech Review와 **같은 등급 체계**(`실행 확인` / `코드 확정` / `미측정`)를 쓴다. 충족 판정에도 근거가 필요하다. "구현돼 있어 보인다" 는 판정이 아니다.

## 단일 점수를 만들지 않는다

`85점`, `충족률 90%` 같은 숫자를 만들지 않는다. 항목마다 무게가 다른데 평균을 내면 **핵심 미충족 하나가 사소한 충족 아홉 개에 묻힌다.**

집계는 판정별 **개수**로만 표현하고, 종합 판단은 문장으로 쓴다. 미충족·부분 충족이 있으면 그중 무엇이 가장 치명적인지 명시한다.

## 과잉 구현을 빠뜨리지 않는다

미달만 보고 초과를 놓치기 쉽다. 의도에 근거가 없는 구현은 **그 자체로 리뷰 대상**이다. 시간이 지나면 "왜 이게 여기 있지" 의 답이 사라진다.

`과잉` 은 "빼라"는 요구가 아니다. **의도 문서에 근거가 없다는 사실**의 기록이다. 실제로 필요한 기능이었다면 의도 쪽을 보강하는 것이 맞다.

## 맥락 적합성

의도를 달성했는지와 별개로, **달성하는 방식**이 레포 맥락에 맞는지 본다.

- 유사 기능이 이미 있는데 다른 방식으로 다시 구현하지 않았는가
- 기존 계층 구조·아키텍처와 같은 방향인가
- 레포 규약 문서(`CLAUDE.md`, `AGENTS.md`, `.claude/skills/**`)와 어긋나지 않는가

취향 차이는 쓰지 않는다. 판단 기준은 아래 리뷰 원칙 8번과 같다.

---

# 리뷰 원칙

## 1. Diff 요약에 그치지 않는다

```
[나쁨] A 파일 수정 / B 메서드 추가 / C DTO 필드 추가
```

변경들이 **합쳐져서 어떤 기능 변화를 만들었는지** 파악한다.

## 2. PR 설명을 그대로 믿지 않는다

PR description은 의도 파악용 참고자료다. 실제 코드가 설명대로 동작하는지 확인하고, **설명과 코드가 어긋나면 그 사실 자체를 리포트한다.**

## 3. 코드 변경을 고립해서 보지 않는다

호출부, 호출 대상, 데이터 모델, 기존 테스트를 읽는다. 특히 다음은 diff 밖에 있어 놓치기 쉽다.

- 공용 헬퍼를 수정했을 때의 **다른 호출자** (조건 판정을 바꾸면 다른 호출자의 동작이 뒤집힐 수 있다)
- 새로 감싼 트랜잭션이 하위 메서드의 전파 속성·`readOnly` 에 주는 영향
- ORM과 raw SQL 혼용으로 인한 **영속성 컨텍스트 stale 문제** (bulk/native 쓰기 후 재조회하면 1차 캐시가 옛 값을 돌려준다)
- 커넥션·리소스 **획득 시점** (lazy proxy 여부에 따라 "점유한다"는 주장이 틀릴 수 있다)
- AOP 어드바이스 적용 순서와, 그 순서가 실제로 결과를 바꾸는지

## 4. 추측과 사실을 구분한다

근거가 부족하면 단정하지 않는다. 위 **근거 등급** 표를 쓴다.

## 5. 개수를 채우지 않는다

문제를 못 찾았으면 못 찾았다고 쓴다.

> 현재 변경 범위에서는 명확한 기술적 문제를 발견하지 못했다.

## 6. 중요한 것을 우선한다

스타일보다 장애·데이터 손실·잘못된 비즈니스 동작·보안·회귀를 우선한다.

## 7. 이 PR이 만든 문제인지 확인한다

레포 전역의 기존 문제를 이 PR의 결함처럼 쓰지 않는다. 지적 전에 확인한다.

```bash
git grep -l "{패턴}" origin/{base} -- {소스경로} | wc -l   # base 에도 있는가
```

기존 관행이라면 Issue가 아니라 `추가 확인 사항` 에 별도 티켓 후보로 남긴다. **다만 이 PR이 새로 쓴 문서·설정이 기존 코드와 어긋나는 경우는 이 PR의 문제다.**

## 8. 개선 방향이 레포 관행을 이탈시키지 않는지 본다

"이렇게 바꾸자"고 제안하기 전에 그 패턴이 레포에서 어떻게 쓰이는지 확인한다. 다수 관행과 반대되는 제안은, 그 관행 자체가 문제라는 근거가 없으면 하지 않는다.
