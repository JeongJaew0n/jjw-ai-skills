# /my-app-init — 새 프로젝트 초기 세팅

## 활성화 조건

사용자가 `/my-app-init` 또는 `$my-app-init` 로 호출한 경우에만 이 스킬을 실행한다. 이름만 언급한 경우는 호출로 보지 않는다 — `disable-model-invocation` 이 그 경로를 차단하므로, 실행하지 말고 슬래시 호출을 안내한다. 프로젝트 시작이나 초기 설정과 내용이 유사하다는 이유만으로 자동 선택하지 않는다.

## 이 스킬의 핵심

**세 가지 질문의 답을 "AI 가 실제로 읽는 자리"에 박는 것**이 이 스킬의 전부다.

산문으로 적어둔 규칙은 지켜지지 않는다. 그래서 답을 두 군데에 넣는다.

| 결정 | 어디에 박히나 | 왜 |
|---|---|---|
| git author | `git config --local user.name/email` | 실제로 커밋 author 를 강제하는 유일한 자리 |
| 커밋·푸시 정책 | `CLAUDE.md` | 다음 세션이 시작할 때 자동으로 읽는 파일 |
| 브랜치 정책 | `CLAUDE.md` | 위와 같음 |

**한 번 정하면 다시 묻지 않는다.** 두 번째 호출 때 `CLAUDE.md` 에 이미 결정 블록이 있으면 재질문하지 않고, 현재 설정을 보여주고 바꿀지만 확인한다.

## 실행 절차

### 0. 대상 확인

인자로 경로가 왔으면 그것, 없으면 현재 디렉터리다. 진행 전에 **지금 무엇이 있는지** 본다.

```bash
"$SKILL_DIR/bin/scaffold.py" detect --root <경로>
ls -a <경로>
```

이미 `CLAUDE.md` 에 결정 블록이 있으면 재실행이다. 현재 값을 보여주고 무엇을 바꿀지 묻는다. 조용히 덮어쓰지 않는다.

`SKILL_DIR` 은 이 `SKILL.md` 가 있는 디렉터리다.

### 1. 세 가지를 묻는다 — 한 번에

`AskUserQuestion` 으로 **세 질문을 한 번에** 던진다. 하나씩 나눠 묻지 않는다. 초기 세팅은 한 호흡에 끝나야 하고, 세 질문은 서로 독립이다.

#### 1.1 git author

`detect` 가 찾아준 실제 계정을 선택지로 만든다. 추상적으로 "어떤 계정?" 이라고 묻지 않는다.

**이 질문이 제일 중요하다.** 개인 계정과 회사 계정이 섞여 있으면 회사 코드를 개인 이메일로 커밋하는 사고가 난다. 공개 저장소에 개인 이메일이 박히는 것도 되돌리기 어렵다 (히스토리 전체를 다시 써야 한다).

선택지는 이렇게 만든다.

- `detect` 의 `git global` 값
- `gh` 로그인 계정들 (GitHub 계정마다 `<id>@users.noreply.github.com` 을 쓸 수 있다는 것도 알려준다)
- 직접 입력

**이메일을 추측해서 채우지 않는다.** 이름만 알고 이메일을 모르면 사용자에게 받는다.

#### 1.2 커밋·푸시 정책

| 선택지 | 뜻 |
|---|---|
| 매번 확인 | AI 는 커밋·푸시를 사용자가 지시할 때만 한다 (기본값으로 권함) |
| 커밋만 자동 | 작업 단위마다 커밋은 알아서, 푸시는 확인받고 |
| 전자동 | 커밋·푸시 모두 알아서 |

**어느 쪽을 골라도 리뷰는 예외다.** 선택지를 보여줄 때 이 점을 함께 알린다 — 코드리뷰·리뷰 문서와 거기서 나온 수정은 '전자동' 을 골라도 사람 확인을 거친다. 리뷰는 사실이 아니라 **의견**이라서, 사람이 읽기 전에 기록에 박히면 틀렸을 때 되돌리기 어렵다. 남의 코드를 지적하는 내용이 확인 없이 올라가는 문제도 있다.

**"전자동" 은 사용자가 주는 지속적 승인이다.** 그렇게 정했으면 `CLAUDE.md` 에 그 사실과 날짜를 명시해, 다음 세션이 근거를 갖고 따를 수 있게 한다. 근거 없이 자동 푸시하는 것과 구분돼야 한다.

#### 1.3 브랜치 정책

| 선택지 | 뜻 |
|---|---|
| main 고정 | 혼자 하는 작은 프로젝트. 브랜치를 만들지 않는다 |
| feature 브랜치 + 로컬 머지 | 작업마다 브랜치, PR 없이 main 으로 머지 |
| feature 브랜치 + PR | 작업마다 브랜치, PR 로 머지 |

### 2. 골격 생성

```bash
"$SKILL_DIR/bin/scaffold.py" apply --root <경로> \
  --author-name "<이름>" --author-email "<이메일>" [--git-init]
```

만들어지는 것:

```
docs/
├── plans/                        AI 작업 계획 (작업당 <slug>/ 폴더)
├── glossary/                     이 프로젝트에서만 통하는 도메인 용어
└── troubleshootings/
    ├── project-specific/         원인이 이 프로젝트 안에 있는 오류
    └── reusable/                 원인이 라이브러리·런타임·OS 에 있는 오류
```

각 폴더에는 용도와 템플릿을 적은 `README.md` 가 함께 들어간다. **빈 폴더로 두지 않는다** — git 이 추적하지 않을뿐더러, 용도를 쓰는 자리에서 설명해야 실제로 지켜진다.

스크립트는 **기존 파일을 덮어쓰지 않는다.** 이미 있는 프로젝트에서 돌려도 안전하고, 여러 번 돌려도 결과가 같다.

### 3. CLAUDE.md 에 결정 기록

`CLAUDE.md` 에 아래 블록을 넣는다. 파일이 이미 있으면 **덮어쓰지 말고 이 블록만 추가**한다.

```markdown
## 프로젝트 규칙 (my-app-init, YYYY-MM-DD 확정)

### git
- author: `<이름> <<이메일>>` — `git config --local` 로 설정돼 있다. 커밋 전 `git config user.email` 로 확인한다.
- 커밋·푸시: <매번 확인 | 커밋만 자동 | 전자동>
- 브랜치: <main 고정 | feature 브랜치 + 로컬 머지 | feature 브랜치 + PR>
- **예외 — 리뷰는 자동 커밋·푸시하지 않는다.** 코드리뷰·리뷰 문서, 그리고 리뷰에서
  나온 수정은 위 정책이 '전자동'이어도 사람이 읽고 판단한 뒤에 커밋한다.
  리뷰는 사실이 아니라 의견이고, 틀린 의견이 먼저 기록에 박히면 되돌리기 어렵다.

### docs
- 여러 단계짜리 작업은 코드를 건드리기 전에 `docs/plans/<slug>/` 에 계획을 먼저 쓴다.
- 원인 찾는 데 시간이 걸린 오류는 `docs/troubleshootings/` 에 남긴다.
  원인이 라이브러리·런타임·OS 에 있으면 `reusable/`, 이 프로젝트의 코드·설정에
  있으면 `project-specific/`.
- 도메인 용어를 새로 만들거나 이름을 바꾸면 `docs/glossary/README.md` 를 먼저 고치고
  코드를 그 이름에 맞춘다. 코드만 바꾸면 용어집이 거짓말이 된다.

### 버전
- **0.x.x 에 머문다. 1.0.0 으로 올리지 않는다.** 내부에서 쓰는 앱이라 공개 API 안정성을
  약속하지 않는다. semver 규격이 `0.y.z` 를 "initial development, 공개 API 를 안정적으로
  보지 않는다" 로 정의하는 것과 같은 자리다.
- 규칙은 **Semantic Versioning** 을 따르되 0.x 구간의 관례를 쓴다.

  | 변경 | 올리는 자리 | 예 |
  |---|---|---|
  | 호환이 깨지는 변경 | **MINOR** (0.y) | `0.3.4` → `0.4.0` |
  | 기능 추가 (호환 유지) | MINOR | `0.3.4` → `0.4.0` |
  | 버그 수정·내부 정리 | PATCH | `0.3.4` → `0.3.5` |

  1.x 에서는 호환 깨짐이 MAJOR 를 올리지만, **0.x 에는 올릴 MAJOR 가 없다.** 그래서
  MINOR 가 그 역할을 대신한다. 이건 semver 규격 본문이 아니라 0.x 구간의 **관례**다
  (Cargo 등이 쓰는 방식).
- 초기값은 `0.1.0` 이다.
- 번호가 사는 곳은 스택의 정본을 쓴다 — `package.json` 의 `version`,
  `pyproject.toml` 의 `[project] version` 등. 정본이 없는 스택이면 루트에 `VERSION`
  파일 한 줄. **두 군데에 적지 않는다.**
- 버전을 올린 커밋에는 무엇이 올랐는지 한 줄 적는다. 번호만 바뀌면 나중에 왜 올렸는지
  알 수 없다.

### 설계
- 기능 묶음 단위는 **<확정한 이름>** 이다. 새 기능은 기존 <이름> 에 넣을지
  새 <이름> 을 만들지 먼저 정하고 시작한다. 코드의 디렉터리·타입 이름도 이 말을 쓴다.
```

`### 설계` 절은 아래 4번에서 멀티 기능 제품으로 판단된 경우에만 넣는다. 단일 기능이면 통째로 뺀다.

`### 버전` 절은 **항상 넣는다.** 선택지가 아니라 이 스킬이 만드는 모든 프로젝트에 적용되는 고정 규칙이다. 버전 번호가 실제로 어느 파일에 들어갈지는 기술 스택을 듣는 4번에서 정해지므로, 그때 확정해 이 절의 마지막 항목을 실제 경로로 채운다.

**날짜는 실제 날짜로 채운다.** "언제 정한 규칙인가" 를 알 수 있어야 나중에 바꿀 때 판단이 선다.

정책 문장은 **행동으로** 쓴다. "자동 커밋 허용" 이 아니라 "작업 단위마다 커밋하고 푸시 전에 확인받는다" 처럼, 다음 세션이 읽고 그대로 실행할 수 있어야 한다.

### 4. 프로젝트 설명을 받아 문서 작성

사용자에게 **이 프로젝트가 무엇인지** 묻는다. 설명 없이 README 를 지어내지 않는다.

받을 것:

- 무엇을 만드는가 (한두 문장)
- 누가 쓰는가
- 기술 스택 (정해졌다면)
- 지금 단계 (아이디어 / 프로토타입 / 실사용)

설명이 짧아도 그것만으로 쓴다. **모르는 것을 채워 넣지 않는다.** 정해지지 않은 항목은 `TBD` 로 남긴다 — 그럴듯한 거짓 문서가 빈 칸보다 나쁘다.

**기술 스택을 들었으면 버전 번호가 살 곳을 확정한다.** 3번의 `### 버전` 절 마지막 항목을 실제 경로로 채우고, 그 파일에 `0.1.0` 을 넣는다.

| 스택 | 정본 |
|---|---|
| Node·TypeScript | `package.json` 의 `version` |
| Python | `pyproject.toml` 의 `[project] version` |
| Rust | `Cargo.toml` 의 `[package] version` |
| 그 외·미정 | 루트 `VERSION` 파일 한 줄 |

스택이 `TBD` 면 `VERSION` 파일로 시작한다. 나중에 매니페스트가 생기면 그쪽으로 옮기고 `VERSION` 은 지운다 — **두 군데에 두면 반드시 어긋난다.**

#### 4-1. 멀티 기능 제품이면 그룹 이름을 정한다

설명을 듣고 **기능이 여러 개인 제품**으로 판단되면(대시보드·관리도구·SaaS·여러 화면을 가진 앱 등) 기능을 묶는 단위를 설계에 넣는다. 기능이 하나뿐인 도구·라이브러리·CLI 면 이 단계를 건너뛴다.

**왜 필요한가.** 기능이 늘어나는 제품은 `src/` 밑이 평평하게 불어나다가 어느 순간 무엇이 무엇과 관련 있는지 알 수 없게 된다. 묶는 단위를 **처음에** 정해두면 새 기능이 생길 때마다 "기존 묶음에 넣을까, 새로 만들까" 라는 질문이 자동으로 나온다. 나중에 도입하려면 이미 흩어진 파일을 다 옮겨야 한다.

`AskUserQuestion` 으로 **그 단위를 이 프로젝트에서 뭐라고 부를지** 묻는다. 선택지는 이렇게 만든다.

| 선택지 | 어울리는 제품 |
|---|---|
| `FeatureGroup` (기본값) | 도메인에 딱 맞는 말이 없을 때 |
| `Module` | 기능이 독립적으로 켜고 끌 수 있는 구조 |
| `Domain` | 업무 영역으로 갈리는 제품 (결제·배송·정산) |
| 직접 입력 | 이미 팀에서 쓰는 말이 있으면 그것 |

사용자가 정하지 않거나 애매하다고 하면 **`FeatureGroup` 으로 진행한다.** 이름을 정하느라 초기 세팅을 붙잡아 두지 않는다. 나중에 바꿀 수 있고, 바꾸는 비용은 지금 못 정하는 비용보다 작다.

**정한 이름은 이름으로만 두지 않는다.** 세 군데에 실제로 반영한다.

1. `CLAUDE.md` 의 `### 설계` 절 (3번 블록)
2. `docs/glossary/README.md` 의 첫 용어 — 이 프로젝트의 도메인 용어 1번이다
3. `CLAUDE.md` 의 `## 구조` 절 — 디렉터리 규약으로 적는다 (예: `src/modules/<이름>/`)

#### 4-2. glossary 초기 작성

사용자의 설명에서 **도메인 용어를 뽑아** `docs/glossary/README.md` 의 표에 채운다. 설명에 나온 말 중 일반적인 뜻과 다르게 쓰이거나, 이 제품에서만 특별한 의미를 갖는 것들이다.

**확실한 것만 적는다.** 사용자가 말하지 않은 용어를 지어내지 않는다. 뽑을 게 없으면 표를 비워두고 "작업하며 채운다" 고 알린다 — 빈 표가 틀린 정의보다 낫다.

뜻이 불확실한 용어가 있으면 **추측해서 적지 말고 물어본다.** 용어집의 값어치는 정확성에 있고, 틀린 정의는 없느니만 못하다.

#### README.md — 사람이 읽는 문서

```markdown
# <프로젝트 이름>

<한 줄 설명>

## 무엇인가
무엇을 해결하는가, 누가 쓰는가.

## 기술 스택
정해진 것만. 미정이면 "TBD".

## 시작하기
설치·실행 명령. 아직 없으면 "TBD".

## 문서
- `docs/plans/` — 작업 계획
- `docs/glossary/` — 도메인 용어
- `docs/troubleshootings/` — 오류와 해결 기록
```

#### CLAUDE.md — AI 가 읽는 문서

3번에서 넣은 규칙 블록 **위에** 프로젝트 맥락을 얹는다.

```markdown
# <프로젝트 이름>

<무엇을 만드는 프로젝트인지 두세 문장. AI 가 첫 턴에 맥락을 잡을 수 있게.>
```

**이 스킬은 커밋하지 않는다.** 커밋 정책을 방금 정했더라도, 그 정책은 앞으로의 작업에 적용되는 것이지 이 초기 세팅 자체에 소급되지 않는다. 첫 커밋은 사용자가 지시할 때 한다.

## 파일 이름은 대문자로 쓴다

`README.md` 와 `CLAUDE.md` 다. 소문자 `claude.md` 로 만들면 **macOS 에서는 동작하고 Linux·CI 에서는 로드되지 않는다.** macOS 기본 파일시스템은 대소문자를 구분하지 않아서 로컬에서는 문제가 드러나지 않다가, 저장소를 리눅스에서 클론하는 순간 AI 가 규칙을 못 읽는 상태가 된다. 증상이 "AI 가 갑자기 규칙을 안 지킨다" 로 나타나서 원인을 찾기 어렵다.

## 동작 원칙

- **기존 파일을 덮어쓰지 않는다.** `README.md`·`CLAUDE.md` 가 이미 있으면 필요한 절만 추가한다. 이미 있는 프로젝트에서 호출될 수 있다.
- **세 질문은 한 번에 묻는다.** 하나씩 나눠 물어 사용자를 붙잡아 두지 않는다.
- **이메일을 추측하지 않는다.** 커밋 author 는 히스토리에 영구히 박히고 되돌리려면 히스토리를 다시 써야 한다.
- **설명을 지어내지 않는다.** 사용자가 말하지 않은 기술 스택·기능·로드맵을 README 에 쓰지 않는다. `TBD` 가 정답이다.
- **용어를 지어내지 않는다.** glossary 에 추측한 정의를 넣지 않는다. 틀린 정의는 없느니만 못하다.
- **그룹 이름 때문에 멈추지 않는다.** 사용자가 애매해하면 `FeatureGroup` 으로 진행한다.
- **재실행을 전제한다.** 두 번째 호출은 재질문이 아니라 현재 설정 확인이다.
- **리뷰 산출물은 어떤 정책에서도 자동 커밋·푸시하지 않는다.** 커밋 정책의 유일한 예외이며,
  이 예외는 사용자에게 묻지 않고 항상 넣는다.
- **첫 커밋은 사용자가 지시할 때 한다.**
