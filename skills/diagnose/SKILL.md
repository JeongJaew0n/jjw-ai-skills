# /diagnose — 근본 원인을 찾고 나서 고친다

## 활성화 조건

사용자가 `/diagnose` 또는 `$diagnose` 로 호출한 경우에만 이 스킬을 실행한다. 이름만 언급한 경우는 호출로 보지 않는다 — `disable-model-invocation` 이 그 경로를 차단하므로, 실행하지 말고 슬래시 호출을 안내한다. 오류 보고나 디버깅과 내용이 유사하다는 이유만으로 자동 선택하지 않는다.

## Iron Law

**근본 원인을 규명하기 전에는 고치지 않는다.**

증상만 고치면 두더지 잡기가 된다. 근본 원인을 건드리지 않은 수정 하나하나가 다음 버그를 더 찾기 어렵게 만든다. 원인을 찾고, 그다음에 고친다.

---

## Phase 0: 기록 위치 확정

**이 단계는 한 번만 한다.** `CLAUDE.md` 에 `diagnose-log:` 줄이 이미 있으면 그 경로를 쓰고 이 단계를 통째로 건너뛴다.

```bash
grep -n "diagnose-log:" CLAUDE.md 2>/dev/null
```

없으면 레포를 훑어 **이미 있는 자리**를 먼저 찾는다. 새 폴더를 만드는 것보다 쓰던 자리에 얹는 게 낫다.

```bash
ls -d docs doc notes wiki .github adr 2>/dev/null
find . -maxdepth 3 -type d \( -iname "*trouble*" -o -iname "*debug*" -o -iname "*postmortem*" -o -iname "*known-issue*" \) -not -path "./.git/*" -not -path "./node_modules/*" 2>/dev/null
```

결과에 따라 `AskUserQuestion` 으로 **한 번** 묻는다.

| 탐지 결과 | 묻는 내용 |
|---|---|
| 오류 기록용 폴더가 이미 있다 | "여기에 남길까요?" — 그 경로를 첫 선택지로 |
| `docs/` 같은 문서 폴더만 있다 | "`<그 폴더>/troubleshootings/` 에 남길까요?" |
| 아무것도 없다 | "`docs/troubleshootings/` 를 만들까요?" |

선택지에는 **"기록하지 않음"** 을 항상 넣는다. 남의 레포이거나 일회성 디버깅이면 파일을 남기지 않는 게 맞다. 거절하면 기록 없이 Phase 1 부터 진행한다.

경로가 정해지면 **`CLAUDE.md` 에 한 줄 남긴다** (파일이 없으면 만들고, 있으면 덧붙인다 — 덮어쓰지 않는다).

```markdown
<!-- diagnose -->
- diagnose-log: `docs/troubleshootings/`
- 오류를 만나면 고치기 전에 이 폴더의 `reusable/` 부터 grep 한다.
```

이 줄이 다음 호출의 재질문을 막고, `/diagnose` 를 부르지 않은 세션도 과거 기록을 참고하게 만든다.

디렉터리는 실제로 기록할 때(Phase 5) 만든다. **여기서 빈 폴더를 만들어 두지 않는다** — 기록이 안 나올 수도 있고, 빈 폴더는 git 이 추적하지도 않는다.

## Phase 1: 근본 원인 조사

가설을 세우기 전에 맥락을 모은다.

1. **증상 수집** — 에러 메시지, 스택 트레이스, 재현 절차를 읽는다. 맥락이 부족하면 `AskUserQuestion` 으로 **한 번에 하나씩** 묻는다.

2. **과거 기록 확인** — Phase 0 의 경로가 있으면 **코드를 읽기 전에** 먼저 본다. 같은 걸 이미 겪었을 수 있다.

   ```bash
   grep -ril "<에러의 핵심 키워드>" <diagnose-log 경로> 2>/dev/null
   ```

   맞는 기록이 있으면 **"과거 기록 적용: `<파일명>`"** 이라고 밝히고 그 내용을 분석에 넣는다. 기록이 지금 코드와 어긋날 수 있으므로 **그대로 믿지 말고 확인한다.**

3. **코드 읽기** — 증상에서 원인 후보까지 코드 경로를 역추적한다. `Grep` 으로 참조를 모두 찾고 `Read` 로 로직을 이해한다.

4. **최근 변경 확인**
   ```bash
   git log --oneline -20 -- <영향받은 파일>
   ```
   전에는 되던 것인가? 무엇이 바뀌었나? 회귀라면 근본 원인은 그 디프 안에 있다.

5. **재현** — 결정적으로 재현되는가? 아니면 증거를 더 모으고 나서 진행한다.

출력: **"근본 원인 가설: …"** — 무엇이 왜 잘못됐는지에 대한 구체적이고 검증 가능한 주장.

---

## Phase 1.5: 범위 선언

가설을 세운 뒤, 고칠 범위를 **말로 선언하고 사용자에게 알린다.**

> "이번 수정은 `src/auth/` 안으로 제한합니다. 그 밖을 건드려야 하면 먼저 말씀드리겠습니다."

버그가 레포 전체에 걸쳐 있거나 범위가 정말 불분명하면 선언을 생략하고 그 이유를 말한다.

**선언한 범위 밖을 고쳐야 할 상황이 오면 조용히 넘어가지 않는다.** 그건 가설이 틀렸다는 신호일 때가 많다. 사용자에게 말하고 Phase 1 로 돌아간다.

## Phase 2: 패턴 분석

알려진 패턴에 맞는지 대조한다.

| 패턴 | 징후 | 볼 곳 |
|---|---|---|
| 경쟁 상태 | 간헐적, 타이밍 의존 | 공유 상태에 대한 동시 접근 |
| 널 전파 | NoMethodError, TypeError | 옵셔널 값의 가드 누락 |
| 상태 손상 | 데이터 불일치, 부분 갱신 | 트랜잭션, 콜백, 훅 |
| 연동 실패 | 타임아웃, 예상 밖 응답 | 외부 API 호출, 서비스 경계 |
| 설정 드리프트 | 로컬은 되고 스테이징/운영은 실패 | 환경변수, 피처 플래그, DB 상태 |
| 스테일 캐시 | 옛 데이터가 보이고 캐시 지우면 고쳐짐 | Redis, CDN, 브라우저 캐시 |

함께 본다.

- `TODOS.md` 에 관련된 기존 이슈가 있는지
- `git log` 로 같은 영역의 과거 수정 — **같은 파일에서 버그가 반복되는 것은 우연이 아니라 구조 문제의 신호다**

**외부 검색**: 위 패턴에 해당하지 않으면 `WebSearch` 로 `"{프레임워크} {일반화된 에러 유형}"`, `"{라이브러리} {컴포넌트} known issues"` 를 찾는다.

**검색 전에 반드시 에러 메시지를 씻는다** — 호스트명·IP·파일 경로·SQL·고객 식별자·사내 정보를 지우고 **에러의 종류**만 검색한다. 안전하게 씻을 수 없을 만큼 구체적인 메시지면 검색하지 않는다. 검색으로 문서화된 해법이나 알려진 의존성 버그가 나오면 Phase 3 의 가설 후보로 올린다.

## Phase 3: 가설 검증

**어떤 수정도 쓰기 전에** 가설을 입증한다.

1. **가설 확인** — 의심 지점에 임시 로그·어설션·디버그 출력을 넣고 재현한다. 증거가 가설과 맞는가?

2. **가설이 틀렸으면** — 다음 가설로 넘어가기 전에 검색을 고려한다(위와 같은 세척 규칙). 그리고 Phase 1 로 돌아가 증거를 더 모은다. **추측하지 않는다.**

3. **3-strike 룰** — 가설 3개가 실패하면 **멈춘다.** `AskUserQuestion` 으로 묻는다.

   ```
   가설 3개를 검증했지만 모두 맞지 않습니다. 단순한 버그가 아니라
   구조 문제일 수 있습니다.

   A) 계속 조사 — 새 가설이 있습니다: [설명]
   B) 사람에게 넘김 — 이 시스템을 아는 사람이 필요합니다
   C) 로그를 심고 대기 — 계측해 두고 다음에 잡습니다
   ```

**적신호** — 아래가 보이면 속도를 늦춘다.

- "일단 급한 대로" — '일단' 은 없다. 제대로 고치거나 넘긴다.
- 데이터 흐름을 추적하기 전에 수정안을 내놓는 것 — 추측하고 있다는 뜻이다.
- 고칠 때마다 다른 곳에서 새 문제가 터지는 것 — 코드가 틀린 게 아니라 **레이어가 틀렸다.**

## Phase 4: 구현

근본 원인이 확인된 뒤에만.

1. **증상이 아니라 근본 원인을 고친다.** 실제 문제를 없애는 가장 작은 변경.

2. **최소 디프** — 건드리는 파일 최소, 바꾸는 줄 최소. 옆의 코드를 리팩터링하고 싶은 충동을 누른다.

3. **회귀 테스트를 쓴다.**
   - 수정 **없이는 실패**할 것 (테스트가 의미 있음을 증명)
   - 수정과 함께 **통과**할 것 (수정이 동작함을 증명)

4. **전체 테스트를 돌리고 출력을 붙인다.** 회귀는 허용하지 않는다.

5. **수정이 5개 파일을 넘으면** `AskUserQuestion` 으로 영향 범위를 알린다.

   ```
   이 수정은 N개 파일을 건드립니다. 버그 수정치고 영향 범위가 넓습니다.
   A) 진행 — 근본 원인이 실제로 이 파일들에 걸쳐 있습니다
   B) 분리 — 핵심 경로만 지금 고치고 나머지는 미룹니다
   C) 재검토 — 더 좁게 가는 방법이 있을지 다시 봅니다
   ```

## Phase 5: 검증과 보고

**새로 검증한다** — 원래 버그 시나리오를 재현해 고쳐졌는지 확인한다. 선택이 아니다.

테스트를 돌리고 출력을 붙인다.

```
DEBUG REPORT
════════════════════════════════════════
증상       : [사용자가 관찰한 것]
근본 원인  : [실제로 무엇이 잘못됐나]
수정       : [무엇을 바꿨나 — file:line]
증거       : [테스트 출력, 재현 시도가 고쳐졌음을 보이는 결과]
회귀 테스트: [새 테스트의 file:line]
관련       : [TODOS.md 항목, 같은 영역의 과거 버그, 구조적 메모]
상태       : DONE | DONE_WITH_CONCERNS | BLOCKED
════════════════════════════════════════
```

### 기록 남기기

Phase 0 에서 경로를 정했고 **원인을 찾는 데 시간이 걸린 오류**라면 기록한다. 바로 보인 오타는 적지 않는다.

기준은 하나다 — **"같은 기술 스택으로 다른 프로젝트를 해도 이 글이 쓸모 있나?"**

| 답 | 위치 | 원인이 어디에 |
|---|---|---|
| 그렇다 | `<경로>/reusable/` | 라이브러리·프레임워크·런타임·OS·외부 서비스 |
| 아니다 | `<경로>/project-specific/` | 이 프로젝트의 코드·설정·데이터 |

파일명은 **증상으로** 짓는다. 나중에 찾는 사람은 원인이 아니라 증상으로 찾는다 — `vite-build-fails-on-node-22.md`.

```markdown
# <증상 한 줄>

## 환경
언어·런타임·라이브러리 버전. 버전이 원인인 경우가 많다.

## 증상
에러 메시지 원문과 재현 조건.

## 원인
왜 그런지. 여기가 이 글의 값어치다.

## 해결
실제로 통한 조치. 통하지 않은 시도도 적으면 다음 사람이 시간을 아낀다.

## 재발 방지
버전 고정·린트 규칙·CI 체크. 없으면 "없음".
```

`reusable/` 에는 프로젝트 이름·내부 모듈명·사내 URL을 넣지 않는다. 그것들이 들어가면 다음 프로젝트에서 못 읽는다.

## Important Rules

- **수정 시도 3회 실패 → 멈추고 구조를 의심한다.** 가설이 틀린 게 아니라 구조가 틀린 것이다.
- **검증할 수 없는 수정은 적용하지 않는다.** 재현하고 확인할 수 없으면 내보내지 않는다.
- **"이러면 고쳐질 겁니다" 라고 말하지 않는다.** 검증하고 증명한다. 테스트를 돌린다.
- **수정이 5개 파일을 넘으면** 진행 전에 영향 범위를 묻는다.
- **멈추는 것은 언제나 괜찮다.** "이건 제 선에서 어렵습니다" 라고 말해도 된다. 나쁜 작업은 안 한 것만 못하다.
- **완료 상태**
  - `DONE` — 근본 원인 확인, 수정 적용, 회귀 테스트 작성, 전체 통과
  - `DONE_WITH_CONCERNS` — 고쳤지만 남은 우려가 있음 (무엇인지 명시)
  - `BLOCKED` — 진행 불가 (무엇이 막는지, 사용자가 무엇을 해야 하는지 명시)
